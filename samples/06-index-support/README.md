# Sample 06: Index Support (CREATE INDEX & DROP INDEX)

This sample demonstrates DeepDiff DB's index comparison and migration features. Learn how to detect index differences between databases and generate CREATE INDEX and DROP INDEX statements safely.

## What You'll Learn

- How DeepDiff DB detects index differences between databases
- Generating CREATE INDEX statements for missing indexes
- Safe DROP INDEX handling with configurable safety modes
- Composite index support (multi-column indexes)
- UNIQUE vs non-unique index detection
- Best practices for index migrations

## Scenario

Your development team has optimized database indexes for better query performance:

**Production Database** has these indexes:
- `users`: `idx_users_email`, `idx_users_username`, `idx_users_status`, `idx_users_created_at`, `idx_users_legacy_search`
- `products`: `idx_products_sku` (UNIQUE), `idx_products_category`, `idx_products_price`, `idx_products_old_search`
- `orders`: `idx_orders_user`, `idx_orders_product`, `idx_orders_status`, `idx_orders_date_status`

**Development Database** has optimized indexes:
- `users`: `idx_users_email` (now UNIQUE), `idx_users_username`, `idx_users_fullname` (NEW)
- `products`: `idx_products_sku` (UNIQUE), `idx_products_category`, `idx_products_active_category` (NEW), `idx_products_name` (NEW)
- `orders`: `idx_orders_user`, `idx_orders_product`, `idx_orders_status_date` (NEW), `idx_orders_user_date` (NEW)

**Changes Summary:**
- 4 indexes added (new optimized indexes)
- 7 indexes removed (obsolete or redundant)
- 1 index modified (idx_users_email changed to UNIQUE)

-- WARNING: Dropping indexes may impact query performance

-- DROP INDEX `idx_users_legacy_search` ON `users`;

**Key Points:**
- CREATE INDEX statements are active (will be executed)
- DROP INDEX statements are commented out (safe by default)
- Modified indexes require manual attention (drop + recreate)

## Configuration Options

### Migration Safety Settings

```yaml
migration:
  # Controls whether DROP INDEX statements are uncommented
  # Default: false (commented for safety)
  allow_drop_index: true

  # Controls whether DROP COLUMN statements are uncommented
  # Default: false (commented for safety)
  allow_drop_column: false

  # Controls whether DROP TABLE statements are uncommented
  # Default: false (commented for safety)
  allow_drop_table: false

  # Adds additional safety warnings for destructive operations
  # Default: true
  confirm_destructive: true
```

## Index Types Supported

| Index Type | CREATE | DROP | Notes |
|------------|--------|------|-------|
| Single Column | Yes | Yes | Basic index on one column |
| Composite | Yes | Yes | Multi-column indexes with preserved order |
| UNIQUE | Yes | Yes | Generates CREATE UNIQUE INDEX |
| Primary Key | No | No | Handled separately (not as index) |

## Database-Specific Behavior

### MySQL
- **CREATE INDEX**: `CREATE INDEX idx_name ON table (col1, col2);`
- **CREATE UNIQUE INDEX**: `CREATE UNIQUE INDEX idx_name ON table (col);`
- **DROP INDEX**: `DROP INDEX idx_name ON table;`

### PostgreSQL
- **CREATE INDEX**: `CREATE INDEX idx_name ON table (col1, col2);`
- **CREATE UNIQUE INDEX**: `CREATE UNIQUE INDEX idx_name ON table (col);`
- **DROP INDEX**: `DROP INDEX idx_name;` (no table reference needed)

### SQLite
- Same syntax as PostgreSQL
- Some limitations with concurrent index operations

## Safety Best Practices

### Before Dropping Indexes

1. **Analyze query patterns** - Ensure the index is not used by critical queries
2. **Check query plans** - Use EXPLAIN to verify queries don't rely on the index
3. **Test in staging** - Apply changes to a non-production environment first
4. **Monitor performance** - Watch for query performance degradation after removal
5. **Have a rollback plan** - Be prepared to recreate dropped indexes

### Index Removal Checklist

- [ ] Index is confirmed unused or redundant
- [ ] No critical queries depend on this index
- [ ] Change tested in non-production environment
- [ ] Performance monitoring in place
- [ ] Rollback script prepared (CREATE INDEX statements)
- [ ] Team notified of upcoming changes

## Handling Modified Indexes

When an index has the same name but different properties (columns, uniqueness), DeepDiff DB reports it as "modified" but cannot automatically migrate it. You must:

1. **Drop the old index** (uncomment the DROP INDEX statement)
2. **Create the new index** (the CREATE INDEX statement is already there)

Example for `idx_users_email` changing from non-unique to unique:
```sql
-- Drop the old non-unique index
DROP INDEX `idx_users_email` ON `users`;

-- Create the new unique index
CREATE UNIQUE INDEX `idx_users_email` ON `users` (`email`);
```

## Troubleshooting

**Problem**: DROP INDEX fails with "index does not exist"

**Solution**: The index may have been already dropped. Check current indexes:
```bash
docker exec -it deepdiff-index-prod-db mysql -uroot -prootpass -e "SHOW INDEX FROM testdb.users"
```

**Problem**: CREATE INDEX fails with "duplicate index"

**Solution**: The index may already exist. Drop it first or skip the CREATE statement.

**Problem**: Performance degradation after dropping index

**Solution**: Recreate the index immediately:
```sql
CREATE INDEX idx_name ON table (columns);
```
