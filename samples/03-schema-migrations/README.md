# Schema Migrations Sample

This sample demonstrates how to use the `schema-migrate` command to generate standalone schema migration scripts. This is useful when you need to migrate schema changes independently from data migrations.

## Overview

The `schema-migrate` command:
- Detects schema differences between two databases
- Generates driver-specific SQL migration scripts
- Provides safe defaults (destructive operations are commented out)
- Supports MySQL, PostgreSQL, and SQLite
- Includes dry-run mode for validation

## Scenario

This sample simulates a real-world scenario where:
- **Production database** (`db_prod`): Has the current production schema
- **Development database** (`db_dev`): Has new schema changes that need to be applied to production

### Schema Differences

The development database includes several schema changes:

**Added Columns:**
- `departments.location` - VARCHAR(255) for department location
- `departments.budget` - DECIMAL(12,2) for department budget
- `employees.start_date` - DATE for employee start date
- `employees.salary` - DECIMAL(10,2) for employee salary

**New Table:**
- `projects` table with columns for project management

**Removed Columns:**
- None in this sample (but would be commented out in migration script)

## 1. Start the Databases

Start the two MySQL databases using Docker Compose:

```bash
docker-compose up -d
```

This will start two MySQL instances:
- `db_prod`: on `localhost:3320` (production database)
- `db_dev`: on `localhost:3321` (development database with schema changes)

The root password for both databases is `rootpassword`.

Wait for the databases to be ready (about 10-15 seconds):

```bash
# Check if databases are ready
docker-compose logs -f
# Press Ctrl+C when you see "ready for connections"
```

## 2. Validate Configuration

The `check` command validates the configuration and connectivity:

```bash
deepdiffdb check --config deepdiffdb.config.yaml
```

Expected output:
```
Config loaded.
Prod: 127.0.0.1:3320/testdb
Dev : 127.0.0.1:3321/testdb
Output directory ready: ./diff-output
Ignore tables: []
Ignore columns: []
Connections OK. Primary keys verified.
```

## 3. Detect Schema Drift

First, let's see what schema differences exist:

```bash
deepdiffdb schema-diff --config deepdiffdb.config.yaml
```

This will show that schema drift has been detected and generate reports in `diff-output/`:
- `schema_diff.json` - Detailed JSON report
- `schema_diff.txt` - Human-readable text report

## 4. Generate Schema Migration (Dry-Run)

Before generating the actual migration file, you can preview it using dry-run mode:

```bash
deepdiffdb schema-migrate --config deepdiffdb.config.yaml --dry-run
```

This will display the generated SQL migration script without writing it to a file. Review the output to understand what changes will be made.

## 5. Generate Schema Migration Script

Now generate the actual migration script:

```bash
deepdiffdb schema-migrate --config deepdiffdb.config.yaml
```

This will create `diff-output/schema_migration.sql` with:
- Transaction-wrapped SQL (BEGIN...COMMIT)
- ALTER TABLE statements to add new columns
- CREATE TABLE statements for new tables (commented with manual creation note)
- Comments for destructive operations (DROP statements)

Expected output:
```
Schema migration generated: diff-output/schema_migration.sql
Changes detected:
  - Table 'departments': 2 columns added
  - Table 'employees': 2 columns added
  - 1 tables added
```

## 6. Review the Generated Migration

Open and review the generated migration script:

```bash
cat diff-output/schema_migration.sql
```

The script will look like:

```sql
BEGIN;

-- Schema Migration Script
-- Generated by DeepDiff DB for mysql
-- WARNING: Review this script carefully before applying to production

-- CREATE TABLES (present in dev but not in prod)
-- WARNING: Manual table creation required - full schema not available
-- CREATE TABLE `projects` (...);

-- Table: departments
ALTER TABLE `departments` ADD COLUMN `location` varchar(255) NULL;
ALTER TABLE `departments` ADD COLUMN `budget` decimal(12,2) NULL;

-- Table: employees
ALTER TABLE `employees` ADD COLUMN `start_date` date NULL;
ALTER TABLE `employees` ADD COLUMN `salary` decimal(10,2) NULL;

COMMIT;
```

## 7. Apply the Migration (Optional)

**⚠️ Warning:** This will modify the production database!

If you want to test applying the migration, you can run it against the prod database:

```bash
# Connect to the database and run the migration
mysql -h 127.0.0.1 -P 3320 -u root -prootpassword testdb < diff-output/schema_migration.sql
```

Or use the `deepdiffdb apply` command (this applies data migrations, but you can adapt it):

```bash
# Note: Currently, apply is for data migration packs
# For schema-only migrations, use the SQL script directly with mysql/psql
```

## 8. Verify the Migration

After applying the migration, you can verify that the schemas match:

```bash
deepdiffdb schema-diff --config deepdiffdb.config.yaml
```

If successful, you should see:
```
Schema match confirmed. No drift detected.
```

## Key Features Demonstrated

1. **Safe Defaults**: Destructive operations (DROP TABLE, DROP COLUMN) are commented out
2. **Driver-Specific SQL**: Uses MySQL-specific syntax (`backticks`, `MODIFY COLUMN`)
3. **Transaction Safety**: All changes wrapped in BEGIN...COMMIT
4. **Dry-Run Mode**: Preview migrations before generating files
5. **Clear Output**: Shows exactly what changes will be applied

## Cleanup

When you're done, stop and remove the Docker containers:

```bash
docker-compose down -v
```

The `-v` flag removes the volumes (database data) as well.

## Use Cases

This approach is ideal for:
- **Separate Schema Workflows**: When you want to apply schema changes separately from data migrations
- **Code Review**: Schema migrations can be reviewed in PRs before applying
- **Gradual Rollout**: Apply schema changes first, then data migrations later
- **CI/CD Integration**: Generate and validate schema migrations in automated pipelines
