# Sample 04: DROP COLUMN Safety and Configuration

This sample demonstrates DeepDiff DB's configurable DROP COLUMN and DROP TABLE support with comprehensive safety features. Learn how to safely manage column removals across development and production databases.

## What You'll Learn

- How to configure DROP COLUMN behavior
- Safety mechanisms for destructive operations
- Difference between safe mode (commented) and active mode
- Best practices for production deployments
- Testing migrations before applying them

## Scenario

Your development team has removed deprecated columns from the schema:
- **Production DB**: Contains `users` table with columns: `id`, `username`, `email`, `phone`, `legacy_status`, `old_address`
- **Development DB**: Contains `users` table with columns: `id`, `username`, `email` (removed: `phone`, `legacy_status`, `old_address`)

You need to generate migration scripts to align production with development.

## Prerequisites

- Docker and Docker Compose installed
- DeepDiff DB installed locally
- Basic understanding of database migrations

## Setup

### 1. Start the Databases

```bash
cd samples/04-drop-column-safety
docker-compose up -d
```

This starts two MySQL databases:
- **Production DB**: Port 3307 - Contains the old schema with deprecated columns
- **Development DB**: Port 3308 - Contains the new schema without deprecated columns

### 2. Verify Database Schema

**Production Database (has extra columns):**
```bash
docker exec -it deepdiff-prod-db mysql -uroot -prootpass -e "DESCRIBE testdb.users"
```

**Development Database (cleaned up):**
```bash
docker exec -it deepdiff-dev-db mysql -uroot -prootpass -e "DESCRIBE testdb.users"
```

## Usage Examples

### Example 1: Safe Mode (Default) - DROP Statements Commented

This is the **recommended approach for production**. DROP statements are commented out by default for safety.

```bash
# Generate migration with default safe settings
deepdiffdb schema-migrate -c deepdiffdb.config.yaml
```

**Output** (`diff-output/schema-migration.sql`):
```sql
BEGIN;

-- Schema Migration Script
-- Generated by DeepDiff DB for mysql
-- WARNING: Review this script carefully before applying to production

-- Table: users
-- DROP COLUMNS (present in prod but not in dev)
-- WARNING: These operations will delete data!
-- IMPORTANT: Review carefully before executing!
-- ALTER TABLE `users` DROP COLUMN `phone`;
-- ALTER TABLE `users` DROP COLUMN `legacy_status`;
-- ALTER TABLE `users` DROP COLUMN `old_address`;

COMMIT;
```

**Benefits:**
- ✅ Safe by default - no accidental data loss
- ✅ Clear visibility of what would be dropped
- ✅ Manual review and approval required
- ✅ Can selectively uncomment specific statements

### Example 2: Active Mode - DROP Statements Enabled

Use this in **non-production environments** or when you're confident about the changes.

**Configuration** (`deepdiffdb-active.config.yaml`):
```yaml
prod:
  driver: mysql
  host: localhost
  port: 3307
  user: root
  password: rootpass
  database: testdb

dev:
  driver: mysql
  host: localhost
  port: 3308
  user: root
  password: rootpass
  database: testdb

output:
  dir: ./diff-output

migration:
  allow_drop_column: true      # Enable DROP COLUMN statements
  allow_drop_table: false       # Keep DROP TABLE commented for safety
  confirm_destructive: true     # Show extra warnings
```

```bash
# Generate migration with DROP COLUMN enabled
deepdiffdb schema-migrate -c deepdiffdb-active.config.yaml
```

**Output** (`diff-output/schema-migration.sql`):
```sql
BEGIN;

-- Schema Migration Script
-- Generated by DeepDiff DB for mysql
-- WARNING: Review this script carefully before applying to production

-- Table: users
-- DROP COLUMNS (present in prod but not in dev)
-- WARNING: These operations will delete data!
-- IMPORTANT: Review carefully before executing!
ALTER TABLE `users` DROP COLUMN `phone`;
ALTER TABLE `users` DROP COLUMN `legacy_status`;
ALTER TABLE `users` DROP COLUMN `old_address`;

COMMIT;
```

**Use Cases:**
- Development/staging environments
- Automated CI/CD pipelines
- When you've backed up data and are ready to proceed

### Example 3: Testing Before Applying

Always test migrations in a safe environment first:

```bash
# 1. Generate the migration
deepdiffdb schema-migrate -c deepdiffdb-active.config.yaml

# 2. Review the generated SQL
cat diff-output/schema-migration.sql

# 3. Test on a database copy first
docker exec -i deepdiff-prod-db mysql -uroot -prootpass testdb < diff-output/schema-migration.sql

# 4. Verify the result
docker exec -it deepdiff-prod-db mysql -uroot -prootpass -e "DESCRIBE testdb.users"
```

## Configuration Options

### Migration Safety Settings

Add a `migration` section to your config file:

```yaml
migration:
  # Controls whether DROP COLUMN statements are uncommented
  # Default: false (commented for safety)
  allow_drop_column: true

  # Controls whether DROP TABLE statements are uncommented
  # Default: false (commented for safety)
  allow_drop_table: false

  # Adds additional safety warnings for destructive operations
  # Default: true
  confirm_destructive: true
```

## Safety Best Practices

### ✅ DO

1. **Always review generated migrations** before applying to production
2. **Test in non-production environments** first
3. **Backup your data** before running destructive migrations
4. **Use safe mode (commented)** for production deployments
5. **Version control** your migration scripts
6. **Document** why columns are being removed

### ❌ DON'T

1. **Don't enable DROP operations** without understanding the impact
2. **Don't skip testing** on non-production databases
3. **Don't assume** the migration will succeed without testing
4. **Don't forget** about foreign key dependencies
5. **Don't bypass** your organization's change management process

## Database-Specific Behavior

### MySQL
- Full DROP COLUMN support
- Statements can be uncommented when `allow_drop_column: true`
- Syntax: `ALTER TABLE table DROP COLUMN column;`

### PostgreSQL
- Full DROP COLUMN support
- Statements can be uncommented when `allow_drop_column: true`
- Syntax: `ALTER TABLE table DROP COLUMN column;`

### SQLite
- **Limited support** - SQLite doesn't support DROP COLUMN directly
- Manual migration required (recreate table without the column)
- DeepDiff DB generates a comment explaining the limitation
- Example: `-- SQLite does not support DROP COLUMN directly. Manual migration required for table users column phone`

## Troubleshooting

**Problem**: Migration fails with foreign key constraint error

**Solution**: DROP foreign keys before dropping columns:
```sql
-- Drop foreign key first
ALTER TABLE users DROP FOREIGN KEY fk_user_status;
-- Then drop the column
ALTER TABLE users DROP COLUMN legacy_status;
```

**Problem**: SQLite migration shows limitation message

**Solution**: SQLite requires manual migration for DROP COLUMN:
1. Create new table without the column
2. Copy data from old table to new table
3. Drop old table
4. Rename new table to old name
