# Sample 05: MODIFY COLUMN - Column Type and Constraint Changes

This sample demonstrates DeepDiff DB's ability to detect and generate ALTER TABLE MODIFY COLUMN statements for column type changes, nullable constraint modifications, and other column definition updates.

## What You'll Learn

- How to detect column type changes
- How to modify nullable constraints
- Safe vs unsafe type conversions
- Database-specific MODIFY COLUMN syntax
- Testing column modifications before applying

## Scenario

Your development team has made several column changes:
- **Type Expansion**: `VARCHAR(50)` → `VARCHAR(255)` (safe)
- **Type Conversion**: `VARCHAR` → `TEXT` (safe)
- **Integer Expansion**: `INT` → `BIGINT` (safe)
- **Nullable Change**: `NOT NULL` → `NULL` (safe)
- **Nullable Restriction**: `NULL` → `NOT NULL` (requires data validation)

## Prerequisites

- Docker and Docker Compose installed
- DeepDiff DB installed locally
- Basic understanding of database migrations

## Setup

### 1. Start the Databases

```bash
cd samples/05-modify-column
docker-compose up -d
```

This starts two MySQL databases:
- **Production DB**: Port 3309 - Contains old column definitions
- **Development DB**: Port 3310 - Contains updated column definitions

### 2. Verify Database Schemas

**Production Database (old definitions):**
```bash
docker exec -it deepdiff-prod-modify mysql -uroot -prootpass -e "DESCRIBE testdb.users"
```

Expected:
```
username     VARCHAR(50)     NOT NULL
email        VARCHAR(100)    NULL
age          INT             NULL
description  VARCHAR(500)    NOT NULL
status       VARCHAR(20)     NOT NULL
```

**Development Database (new definitions):**
```bash
docker exec -it deepdiff-dev-modify mysql -uroot -prootpass -e "DESCRIBE testdb.users"
```

Expected:
```
username     VARCHAR(255)    NOT NULL    (expanded from 50)
email        VARCHAR(100)    NOT NULL    (changed to NOT NULL)
age          BIGINT          NULL        (expanded from INT)
description  TEXT            NOT NULL    (converted from VARCHAR(500))
status       VARCHAR(50)     NULL        (expanded and made nullable)
```

## Usage Examples

### Example 1: Generate Migration Script

```bash
deepdiffdb schema-migrate -config deepdiffdb.config.yaml
```

**Output** (`diff-output/schema_migration.sql`):
```sql
BEGIN;

-- Schema Migration Script
-- Generated by DeepDiff DB for mysql
-- WARNING: Review this script carefully before applying to production

-- Table: users
ALTER TABLE `users` MODIFY COLUMN `age` BIGINT NULL;
ALTER TABLE `users` MODIFY COLUMN `description` TEXT NOT NULL;
ALTER TABLE `users` MODIFY COLUMN `email` VARCHAR(100) NOT NULL;
ALTER TABLE `users` MODIFY COLUMN `status` VARCHAR(50) NULL;
ALTER TABLE `users` MODIFY COLUMN `username` VARCHAR(255) NOT NULL;

COMMIT;
```

### Example 2: Understanding the Changes

Each MODIFY COLUMN statement updates the complete column definition:

**Type Expansion (Safe)**:
```sql
-- VARCHAR(50) → VARCHAR(255)
ALTER TABLE `users` MODIFY COLUMN `username` VARCHAR(255) NOT NULL;
```
✅ Safe - no data loss, existing data fits in larger field

**Type Conversion (Safe)**:
```sql
-- VARCHAR(500) → TEXT
ALTER TABLE `users` MODIFY COLUMN `description` TEXT NOT NULL;
```
✅ Safe - TEXT can hold all VARCHAR data

**Integer Expansion (Safe)**:
```sql
-- INT → BIGINT
ALTER TABLE `users` MODIFY COLUMN `age` BIGINT NULL;
```
✅ Safe - BIGINT can hold all INT values

**Nullable Relaxation (Safe)**:
```sql
-- NOT NULL → NULL
ALTER TABLE `users` MODIFY COLUMN `status` VARCHAR(50) NULL;
```
✅ Safe - making column nullable doesn't affect existing data

**Nullable Restriction (Requires Validation)**:
```sql
-- NULL → NOT NULL
ALTER TABLE `users` MODIFY COLUMN `email` VARCHAR(100) NOT NULL;
```
⚠️  Requires validation - ensure no NULL values exist first!

### Example 3: Testing Before Applying

Always test migrations in a safe environment:

```bash
# 1. Generate the migration
deepdiffdb schema-migrate -config deepdiffdb.config.yaml

# 2. Review the generated SQL
cat diff-output/schema_migration.sql

# 3. Check for NULL values before adding NOT NULL constraint
docker exec deepdiff-prod-modify mysql -uroot -prootpass -e \
  "SELECT COUNT(*) FROM testdb.users WHERE email IS NULL"

# 4. If there are NULLs, update them first
docker exec deepdiff-prod-modify mysql -uroot -prootpass -e \
  "UPDATE testdb.users SET email = 'unknown@example.com' WHERE email IS NULL"

# 5. Dry-run to validate the migration (recommended)
deepdiffdb apply -config deepdiffdb.config.yaml -pack diff-output/schema_migration.sql -dry-run

# 6. Apply the migration to production database
deepdiffdb apply -config deepdiffdb.config.yaml -pack diff-output/schema_migration.sql

# 7. Verify the result
docker exec deepdiff-prod-modify mysql -uroot -prootpass -e \
  "DESCRIBE testdb.users"
```

## Database-Specific Behavior

### MySQL
- Uses `MODIFY COLUMN` with full column definition
- Single statement per column
- Must specify complete definition (type + NULL constraint)
- Syntax: `ALTER TABLE table MODIFY COLUMN column type [NOT NULL]`

**Example:**
```sql
ALTER TABLE `users` MODIFY COLUMN `username` VARCHAR(255) NOT NULL;
```

### PostgreSQL
- Uses separate `ALTER COLUMN TYPE` and `SET/DROP NOT NULL` statements
- Can use `USING` clause for complex type conversions
- More granular control over changes

**Example:**
```sql
-- Type change
ALTER TABLE "users" ALTER COLUMN "age" TYPE BIGINT;

-- Nullable change
ALTER TABLE "users" ALTER COLUMN "email" SET NOT NULL;
```

### SQLite
- **Very Limited** - doesn't support MODIFY COLUMN directly
- Requires table recreation:
  1. Create new table with updated schema
  2. Copy data from old table
  3. Drop old table
  4. Rename new table

**Example:**
```sql
-- SQLite does not support MODIFY COLUMN. Manual migration required for table users column age
```

## Type Compatibility Matrix

### ✅ Safe Type Changes (No Data Loss)

| From          | To            | MySQL | PostgreSQL | SQLite | Notes |
|---------------|---------------|-------|------------|--------|-------|
| VARCHAR(n)    | VARCHAR(m>n)  | ✅    | ✅         | ❌     | Expansion only |
| VARCHAR       | TEXT          | ✅    | ✅         | ❌     | Safe conversion |
| INT           | BIGINT        | ✅    | ✅         | ❌     | Size expansion |
| DECIMAL(m,n)  | DECIMAL(p>m,q≥n) | ✅ | ✅         | ❌     | Precision expansion |
| NOT NULL      | NULL          | ✅    | ✅         | ❌     | Relaxing constraint |

### ⚠️ Potentially Unsafe Changes (May Cause Data Loss)

| From          | To            | Risk | Solution |
|---------------|---------------|------|----------|
| VARCHAR(100)  | VARCHAR(50)   | Truncation | Check max length first |
| BIGINT        | INT           | Overflow | Validate value ranges |
| TEXT          | VARCHAR(n)    | Truncation | Check data lengths |
| NULL          | NOT NULL      | Constraint violation | Remove NULLs first |
| DECIMAL(10,2) | DECIMAL(5,2)  | Overflow | Validate values |

## Best Practices

### ✅ DO

1. **Test in non-production first**
   ```bash
   # Always test on a copy of production data
   ```

2. **Validate data before restricting constraints**
   ```sql
   -- Before adding NOT NULL, check for NULLs
   SELECT COUNT(*) FROM users WHERE email IS NULL;
   ```

3. **Use safe type expansions**
   - VARCHAR(50) → VARCHAR(100) ✅
   - INT → BIGINT ✅
   - DECIMAL(5,2) → DECIMAL(10,2) ✅

4. **Review generated SQL carefully**
   ```bash
   cat diff-output/schema_migration.sql
   ```

5. **Backup before applying**
   ```bash
   mysqldump -u root -p testdb > backup.sql
   ```

### ❌ DON'T

1. **Don't shrink column sizes without validation**
   - VARCHAR(100) → VARCHAR(50) ❌ (may truncate)

2. **Don't add NOT NULL without checking for NULLs**
   - Will fail if NULL values exist

3. **Don't convert incompatible types**
   - TEXT → INT ❌ (will fail if non-numeric data)

4. **Don't skip testing**
   - Always test migrations before production

5. **Don't ignore warnings**
   - Pay attention to data loss warnings

## Common Scenarios

### Scenario 1: Expanding VARCHAR Size

**Problem**: Field is too small for new data
```sql
username VARCHAR(50)  -- Current
username VARCHAR(255) -- Needed
```

**Solution**:
```sql
ALTER TABLE `users` MODIFY COLUMN `username` VARCHAR(255) NOT NULL;
```
✅ Safe - no data loss

### Scenario 2: Making Column Nullable

**Problem**: Need to allow NULL values
```sql
status VARCHAR(20) NOT NULL  -- Current
status VARCHAR(20) NULL       -- Needed
```

**Solution**:
```sql
ALTER TABLE `users` MODIFY COLUMN `status` VARCHAR(20) NULL;
```
✅ Safe - relaxing constraint

### Scenario 3: Adding NOT NULL Constraint

**Problem**: Need to enforce data presence
```sql
email VARCHAR(100) NULL     -- Current
email VARCHAR(100) NOT NULL -- Needed
```

**Solution**:
```bash
# 1. Check for NULLs
SELECT COUNT(*) FROM users WHERE email IS NULL;

# 2. If NULLs exist, fix them
UPDATE users SET email = 'unknown@example.com' WHERE email IS NULL;

# 3. Apply constraint
ALTER TABLE `users` MODIFY COLUMN `email` VARCHAR(100) NOT NULL;
```
⚠️ Requires data cleanup first

### Scenario 4: Integer Size Expansion

**Problem**: Values approaching limit
```sql
user_id INT          -- Current (max ~2 billion)
user_id BIGINT       -- Needed (max ~9 quintillion)
```

**Solution**:
```sql
ALTER TABLE `users` MODIFY COLUMN `user_id` BIGINT NOT NULL;
```
✅ Safe - size expansion

## Troubleshooting

**Problem**: Migration fails with "Data too long for column"

**Solution**:
```sql
-- Find problematic rows
SELECT id, LENGTH(column_name) as len
FROM table_name
WHERE LENGTH(column_name) > new_size;

-- Fix or investigate
```

**Problem**: Cannot add NOT NULL constraint

**Solution**:
```sql
-- Find NULL values
SELECT COUNT(*) FROM table WHERE column IS NULL;

-- Update or delete them
UPDATE table SET column = default_value WHERE column IS NULL;
```

**Problem**: PostgreSQL type conversion fails

**Solution**:
```sql
-- Use USING clause for complex conversions
ALTER TABLE users ALTER COLUMN age TYPE BIGINT USING age::BIGINT;
```
